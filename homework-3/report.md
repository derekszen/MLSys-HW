# CKPT-3 存储子系统实验报告

**结论：**当 Host 能保留被挤出的前缀时，恢复缓存可替代重算；工作集超过 Host 预算或前缀不再复用时，写回仍有成本，却不能节省 prefill。本文先给出双芯片主实验，最后用独立的单芯片实验检验这个解释。

在课程机 Ascend 910 上，Qwen3.5-0.8B 和 4B 均以 TP=2 运行。两模型在相同的 9 块设备缓存下各交替访问两条提示词。较大 Host 池在每个 rank 上恢复三次已经离开 HBM 的前缀；两模型生成的 token ID 均与关闭卸载时逐个相同。缩小 Host 池或改用独立前缀，可以分别观察容量淘汰与无复用写回的代价。

## 缓存生命周期及容量

TokenSpeed 的 C++ scheduler 管理 HBM 预分配池和 Host 两个池。普通 L2 条目由 token 序列的链式哈希、缓存组及块偏移定位。计算已经提交的完整页和相应状态检查点可以写回到每个 rank 的 pinned CPU buffer。普通写回持有设备源块，写回事件完成后才发布 Host 条目、释放该引用。未被请求引用的 HBM 缓存可在调度器需要空间时回收。Host 容量不足时，按现有访问与复用优先级淘汰可回收块，正在搬运或被恢复镜像引用的块保留。前缀未命中时从现有检查点后的 token 开始计算，完全未命中时从零状态重新 prefill。

暂挂请求使用其请求 ID 关联私有镜像及 slot。镜像中已发布的页可引用 L2，未发布页和 slot 数据进入独立快照池。引擎只选择没有在途 forward 的请求作为暂挂候选。写回与 slot 导出在同一写流完成，执行流等待写入 fence 后才可覆盖本轮重新授予的 HBM 页。恢复先分配新设备块，再从 Host 复制镜像。恢复 ACK 到达前，请求处于 Restoring，调度器不会提交下一步推理。TP=2 各 rank 处理各自的 payload，CacheOpHooks 对 ACK 集合求交，两个 rank 一致确认后提交恢复。私有快照始终绑定原请求，相同 token 前缀可有意共享已经发布的不可变缓存。不同前缀通过内容键匹配，复现脚本交替验证两条独立序列。

`--kvstore-size` 配置每个 rank 的 L2 逻辑容量，单位为十进制 GB。`--kvstore-ratio` 按设备 LCM 块数配置容量，各 rank 统一可分配的块数。`--retraction-snapshot-host-gb` 配置私有池，独立于 L2。私有镜像保留到恢复或请求释放，容量不足时有界等待或终止容量受阻的请求。性能对照的关闭组同时关闭 L2 和快照池，并保留 Device 前缀缓存。该组若在设备压力下终止请求，保留失败记录，并在双方可运行的相同预算下另做延迟对照。

## 混合状态及恢复位置

| 状态 | 保存粒度 | 恢复边界 |
| --- | --- | --- |
| Attention K、V | 按缓存组及缓存页复制本 rank 的 K、V payload，尾页保持其有效 token 边界 | 恢复检查点之前所需的所有页。下一步消费该边界后的输入。 |
| 递归 SSM | rank 本地每层 FP32 状态，按 state group 的快照槽复制 | 与所选 token 边界严格匹配。前缀复用装入输入槽，暂挂恢复还原快照中的槽。 |
| 卷积历史 | 同一 state group 的完整卷积窗口，使用激活 dtype | 与递归状态同一上下文位置，后续 token 更新窗口。 |

设恢复快照已计算范围为 `[0,T)`。对运行中的请求，镜像包含同一 `T` 的 KV、递归和卷积状态，恢复继续消费位置 `T` 的待处理输入。对新请求的前缀复用，调度器联合匹配 KV 和 state checkpoint，选择满足缓存及 logits 计算约束的边界，然后计算提示词的剩余范围。生成第一个 token 所需的末尾输入至少执行一次。日志中的 `prefill` 三元组依次记录已调度前缀长度、回放长度和本次实际输入长度。暂挂日志另外记录 `computed=T`，区分已计算位置与已采样但仍未执行 forward 的 token。

Ascend 选用直接字节范围 DMA。普通 L2 批量恢复中，每个缓存消费者等待同一个完整拷贝事件，涵盖 K、V、递归和卷积状态。私有镜像恢复复用现有 ACK 和 slot 导入流程。拷贝命令只提交给所属 rank，在 rank 间对齐 op ID 和前缀位置。

## 实验设置与判据

0.8B 使用物理芯片 6、7 和 BF16，4B 使用芯片 4、5 和 FP16，4B 的输出头以 FP32 计算。两组的递归状态均为 FP32。两模型都按 TP=2 分片，使用贪心解码、长度 128 的分块 prefill 和容量为两个请求的调度器。通过同一 TokenSpeed 模型在关闭 Host 池时的输出来检验恢复；逐请求比对全部 token ID，并要求所选 token 的 logprob 绝对误差不超过 0.15。两 rank 的前缀位置及完成传输的操作 ID 必须一致。[实现与复现命令](README.md)

高复用先输入两条各 192 token 的种子，然后交替访问这两个前缀，每次增加一个新 token；每次访问前插入一条独立的 192-token 请求以挤出 HBM 缓存。低复用保持请求长度和次数相同，全部使用独立前缀。两组都包含 4 个目标请求，每个生成 8 个 token；种子与填充请求各生成 1 个。延迟是 4 个目标请求的端到端中位数，包含恢复、剩余 prefill 和解码。预热后吞吐取最后三对填充与目标请求，分子为 27 个实际生成的 token，分母为这些调用的总墙钟时间。原始全程吞吐另存，包含首次内核启动。共享服务器上的每种配置各运行一次，下面的差异只描述本次工作负载。

## 容量与性能实测

Host 占用列为每个 rank 的 L2 峰值已认领容量与预分配容量，单位 MiB。命中与未命中在请求进入调度器时计数，纯 Device 命中不计入两者。淘汰按 Host 缓存组块计数。关闭组不查询 Host。

| 模型 | 访问 / Host | Host 占用 / 分配 | 命中 / 未命中 / 淘汰 | 目标延迟（秒） | 预热后吞吐（token/s） |
| --- | --- | ---: | ---: | ---: | ---: |
| 0.8B | 高 / 关闭 | 0 / 0 | 0 / 0 / 0 | 1.462 | 3.87 |
| 0.8B | 高 / 大池 | 186 / 216 | 3 / 6 / 0 | 0.731 | 5.31 |
| 0.8B | 高 / 小池 | 24 / 24 | 0 / 9 / 42 | 1.425 | 3.74 |
| 0.8B | 低 / 关闭 | 0 / 0 | 0 / 0 / 0 | 1.566 | 3.53 |
| 0.8B | 低 / 大池 | 186 / 216 | 0 / 10 / 0 | 1.616 | 3.39 |
| 4B | 高 / 关闭 | 0 / 0 | 0 / 0 / 0 | 1.946 | 2.86 |
| 4B | 高 / 大池 | 496 / 576 | 3 / 6 / 0 | 1.001 | 3.78 |
| 4B | 高 / 小池 | 64 / 64 | 0 / 9 / 42 | 2.232 | 2.56 |
| 4B | 低 / 关闭 | 0 / 0 | 0 / 0 / 0 | 1.846 | 2.99 |
| 4B | 低 / 大池 | 496 / 576 | 0 / 10 / 0 | 1.845 | 3.00 |

设备池容量始终为每 rank 9 个可用 LCM 块；高复用组的 Device 空块最低降至 0。两模型的关闭组都只有首次回访能在 Device 找到 192 个 token，后三次回访各重算 193 个提示 token。大池组则三次从 Host 恢复 [0,192)，每次只计算新增的第 193 个输入，合计少做 576 个 prefill token。两个模型的大池组在最后一次写回确认后均有 9 块可再次分配。请求结束且数据仍保留在 Device 时，可回收数可以大于空块数。

在高复用迹线上，大池把 0.8B 的目标延迟从 1.462 秒降至 0.731 秒，把 4B 从 1.946 秒降至 1.001 秒。小池的 4 个 Host 块不足以保留回访工作集，两模型各发生 42 次组块淘汰，回访退化为重算且仍产生写回。低复用时两模型各有 10 次未命中，均未触发恢复；0.8B 的吞吐从 3.53 降至 3.39 token/s，4B 的两次测量接近。

## 活跃会话恢复与资源回收

每个模型在相同的 16 个 Device 块下运行 4 批，每批同时提交两条互不相同的 192-token 请求并各生成 8 个 token。参考组连续解码；实验组关闭普通 L2，给私有快照池配置 0.25 GB，在解码期间每隔 4 个调度计划尝试暂挂一次。每个模型的 8 条输出共 64 个 token 全部与各自参考一致。0.8B 的最大 logprob 绝对误差为 0，4B 为 0.00769。

| 模型 | 每 rank 暂挂 / 恢复 | 单向累计 payload（MiB/rank） | 快照块峰值 / 总块数 | 结束时空闲块 | 批延迟，参考 / 暂挂（秒） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0.8B | 8 / 8 | 95.85 | 5 / 39 | 39 | 2.298 / 2.439 |
| 4B | 11 / 11 | 363.31 | 5 / 14 | 14 | 3.196 / 3.454 |

两个模型实际暂挂时已计算的位置均落在 193–198 之间。0.8B 例如有同一请求先在 T=194、后在 T=197 暂挂；4B 有同一请求在 T=196 重复暂挂。每次暂挂日志中的序列长度都是 T+1，恢复后直接消费位置 T 的待处理 token，已计算区间 [0,T) 的重算长度为 0。两模型各自的双 rank 均确认了全部搬运，快照池回收了所有已认领块。rank 0 上，0.8B 的写出 / 恢复完成时间中位数为 79.7 / 73.7 ms，4B 为 100.6 / 5.4 ms。两模型各 rank 的槽位额外预留 432 字节；两芯片末次 HBM 总量在参考与暂挂组分别均为 5,146 MB 和 16,770 MB。
